Question 1Correct

In Namespace `team-dev`, there is an existing CiliumNetworkPolicy `default-allow` which allows all namespace-internal traffic and cluster DNS.
The task is to create two new Layer 3 and Layer 4 CiliumNetworkPolicy named `team-dev` and `team-dev-2` that:

1. Enables `**Mutual Authentication**` for outgoing traffic from Pods with label `role=database` to Pods with label `role=api-service`.

2. Denies outgoing **ICMP traffic** from Pods of Deployment `stuff` to Pods behind Service `backend`.


Your answer is correct

solution

#### Explanation

**Step 1: Verify Pod labels and IPs**



1. kubectl get pod -n team-dev --show-labels -o wide



Example output:



1. NAME                         ...     IP           ...   LABELS
2. database-0                   ...   10.244.2.122    ...   ...,role=database
3. api-service-57f557cd65-rhzd7 ...   10.244.1.171    ...   ...,role=api-service
4. api-service-57f557cd65-xcqwz ...   10.244.2.44     ...   ...,role=api-service
5. stuff-866696fc57-6ccgr       ...   10.244.1.15     ...   ...,role=stuff
6. stuff-866696fc57-d8qk4       ...   10.244.2.222    ...   ...,role=stuff
7. backend-0                    ...   10.244.3.10     ...   ...,role=backend



**Step 2: Create CiliumNetworkPolicy to deny ICMP traffic from stuff to backend**



1. # cnp-icmp-deny.yaml
2. apiVersion: "cilium.io/v2"
3. kind: CiliumNetworkPolicy
4. metadata:
5.   name: team-dev
6.   namespace: team-dev
7. spec:
8.   endpointSelector:
9.     matchLabels:
10.       role: stuff  # Pods behind Deployment "stuff"
11.   egressDeny:
12.   - toEndpoints:
13.     - matchLabels:
14.         role: backend  # Pods behind Service "backend"
15.     icmps:
16.     - fields:
17.       - type: 8
18.         family: IPv4
19.       - type: EchoRequest
20.         family: IPv6



21. kubectl apply -f cnp-icmp-deny.yaml



**Step 3: Create CiliumNetworkPolicy to enforce Mutual Authentication from database → api-service**



1. # cnp-mtls.yaml
2. apiVersion: "cilium.io/v2"
3. kind: CiliumNetworkPolicy
4. metadata:
5.   name: team-dev-2
6.   namespace: team-dev
7. spec:
8.   endpointSelector:
9.     matchLabels:
10.       role: database
11.   egress:
12.   - toEndpoints:
13.     - matchLabels:
14.         role: api-service
15.     authentication:
16.       mode: "required"  # Enable Mutual Authentication



17. kubectl apply -f cnp-mtls.yaml



**Step 4: Verify policies are applied**



1. # Check applied CiliumNetworkPolicies
2. kubectl get cnp -n team-dev

3. # Test ICMP block (stuff -> backend)
4. kubectl exec -n team-dev stuff-866696fc57-6ccgr -- ping -c 1 <backend-pod-IP>
5. # Should fail due to ICMP deny

6. # Test outgoing traffic from database to api-service (Mutual Authentication enforced)
7. kubectl exec -n team-dev database-0 -- curl http://<api-service-pod-IP>
8. # Connection should succeed only if authenticated



**Explanation**

- `endpointSelector` → selects Pods the policy applies to.

- `egressDeny` → blocks ICMP traffic from `stuff` Pods to `backend` Pods.

- `egress.authentication.mode=required` → enforces Mutual TLS for traffic from `database` to `api-service`.

- By keeping `default-allow` intact, intra-namespace and DNS traffic remain allowed.




⚠️ Notes:

- ICMP types 8 (IPv4) and EchoRequest (IPv6) are the ones used for ping.

- Mutual Authentication ensures encrypted and verified communication between selected Pods.

- Policies are additive; multiple CNPs can coexist to enforce different rules for different traffic flows.

Question 2Correct

For security hardening, enforce a **Seccomp profile** on Pods in Namespace `secure-app`.

- Create a custom Seccomp profile that allows only basic system calls (`read`, `write`, `exit`, `sigreturn`).

- Apply the Seccomp profile to the Deployment `webapp` to restrict system calls for its containers.

- Verify that the Pod is running and that the Seccomp profile is enforced.


Your answer is correct

solution

#### Explanation

**Step 1: Create a custom Seccomp profile**


Save the profile as `/opt/course/2/seccomp-profile.json`:



1. {
2.   "defaultAction": "SCMP_ACT_ERRNO",
3.   "architectures": [
4.     "SCMP_ARCH_X86_64",
5.     "SCMP_ARCH_X86",
6.     "SCMP_ARCH_X32"
7.   ],
8.   "syscalls": [
9.     {
10.       "names": ["read", "write", "exit", "sigreturn"],
11.       "action": "SCMP_ACT_ALLOW"
12.     }
13.   ]
14. }



15. mv /opt/course/2/seccomp-profile.json /var/lib/kubelet/seccomp/profiles/



**Step 2: Apply the Seccomp profile to the Deployment**



Edit the Deployment webapp in `**secure-app**` namespace:



1. ---
2. apiVersion: apps/v1
3. kind: Deployment
4. metadata:
5.   name: webapp
6.   namespace: secure-app
7. spec:
8.   replicas: 2
9.   selector:
10.     matchLabels:
11.       app: webapp
12.   template:
13.     metadata:
14.       labels:
15.         app: webapp
16.     spec:
17.       containers:
18.       - name: webapp
19.         image: nginx:latest
20.         securityContext:
21.           seccompProfile:
22.             type: Localhost
23.             localhostProfile: profiles/seccomp-profile.json



24. kubectl apply -f /opt/course/2/webapp.yaml



**Step 3: Verify the Seccomp profile enforcement**



1. # Check Pods
2. kubectl get pod -n secure-app

3. # Describe a Pod to see Seccomp profile applied
4. kubectl describe pod <pod-name> -n secure-app | grep -i seccomp

5. # Test that disallowed syscalls fail
6. kubectl exec -it <pod-name> -n secure-app -- sh -c "exec /bin/bash"
7. # Should fail due to Seccomp restrictions
8. # Example: attempt a disallowed syscall (e.g., execve of /bin/bash)



**Explanation**

- Seccomp (Secure Computing Mode) restricts the system calls a container can make, limiting kernel-level attack surface.

- `SCMP_ACT_ERRNO` denies all syscalls by default.

- `Localhost` profile type allows using a custom JSON Seccomp file stored locally on the node.

- By restricting to only `read`, `write`, `exit`, and `sigreturn`, the container can perform basic I/O without executing potentially dangerous syscalls




⚠️ Notes:

- Ensure the `seccomp-profile.json` file exists on each node under the correct path referenced in the Deployment.

- Custom Seccomp profiles enhance container security by preventing kernel exploitation through syscalls.

Question 3Correct

A Pod in namespace `ci-cd` mounts `**/var/run/docker.sock**` from the host.
By default, the socket is **owned by root:docker** with permissions `0660`, allowing **any user in group docker** to control the Docker daemon.

Your task is to **reduce the risk by restricting file permissions** without breaking essential CI/CD jobs.
Specifically:

1. Change ownership and group of `**docker.sock**` inside the Pod.

2. Limit access using chmod so that **only the intended user** can access the socket.

3. Verify that the container cannot run arbitrary containers if not authorized.


Your answer is correct

solution

#### Explanation

**Step 1: Inspect** `**docker.sock**` **permissions**



1. kubectl exec -it <pod-name> -n ci-cd -- ls -l /var/run/docker.sock
2. # Example output:
3. # srw-rw---- 1 root docker 0 Aug 25 16:00 /var/run/docker.sock



**Step 2: Adjust permissions and ownership inside Pod**



1. kubectl exec -it <pod-name> -n ci-cd -- chown 65535:65535 /var/run/docker.sock
2. kubectl exec -it <pod-name> -n ci-cd -- chmod 0600 /var/run/docker.sock

3. # 65535:65535 → unprivileged user (nobody)
4. # 0600 → only owner can read/write



**Step 3: Apply** `**securityContext**` **for the container**



1. securityContext:
2.   runAsUser: 65535
3.   runAsGroup: 65535
4.   readOnlyRootFilesystem: true
5.   allowPrivilegeEscalation: false
6.   capabilities:
7.     drop: ["ALL"]



**Step 4: Verify the changes**



1. kubectl exec -it <pod-name> -n ci-cd -- ls -l /var/run/docker.sock
2. # srw------- 1 nobody nobody 0 Aug 21 16:15 /var/run/docker.sock

3. # Try running docker commands
4. kubectl exec -it <pod-name> -- docker ps   # should fail if not owner



**Explanation**

- `**/var/run/docker.sock**` is a **hostPath socket**, granting full Docker access to anyone who can write to it.

- Changing **ownership to** `**unprivileged**` **user** prevents rootless escalation through the socket.

- Restricting **chmod to 0600** ensures no other users in the container or host group can control Docker.

- Combined with `**runAsUser**` and `**drop: ALL capabilities**`, this **significantly reduces the attack surface**.




⚠️ Note:

- In real environments, it's better to avoid mounting host `**docker.sock**`. Consider remote Docker API with TLS or Docker-in-Docker.

Question 5Correct

Create a default-deny NetworkPolicy named `default-deny` in the `testing` namespace that blocks all Egress traffic for all Pods.
`Optionally`, allow DNS egress if needed.

Your answer is correct

solution

#### Explanation

By applying a default-deny Egress NetworkPolicy with an empty `podSelector`, all Pods in the namespace are restricted from initiating outbound connections.
Specific exceptions like DNS can be allowed by adding `egress` rules.



**Commands / Steps**



1. # default-deny-np.yaml
2. apiVersion: networking.k8s.io/v1
3. kind: NetworkPolicy
4. metadata:
5.   name: default-deny
6.   namespace: testing
7. spec:
8.   podSelector: {}       # Applies to all pods in the testing namespace
9.   policyTypes:
10.   - Egress
11.   # No rules in egress list blocks all egress traffic



`**Optional**`:  Allow DNS `egress`



1. # Optional: allow DNS egress to kube-system namespace
2. apiVersion: networking.k8s.io/v1
3. kind: NetworkPolicy
4. metadata:
5.   name: default-deny
6.   namespace: testing
7. spec:
8.   podSelector: {}
9.   policyTypes:
10.   - Egress
11.   egress:
12.   - to:
13.     - namespaceSelector:
14.         matchLabels:
15.           name: kube-system
16.     ports:
17.     - protocol: UDP
18.       port: 53



19. # You can also allow egress to DNS at all (into any direction)
20. apiVersion: networking.k8s.io/v1
21. kind: NetworkPolicy
22. metadata:
23.   name: default-deny
24.   namespace: testing
25. spec:
26.   podSelector: {}
27.   policyTypes:
28.   - Egress
29.   egress:
30.   - to: []           # allow egress into any direction
31.     ports:
32.     - protocol: UDP
33.       port: 53

34. # Apply the default-deny NetworkPolicy
35. kubectl apply -f default-deny-np.yaml



**Verification Step:**



1. # Ensure all Pods are restricted from egress
2. kubectl get networkpolicy -n testing
3. kubectl describe networkpolicy default-deny -n testing



⚠️ Note:

- NetworkPolicy with empty `podSelector` applies to all Pods in the namespace.

- By default, an empty `egress` array `[]` blocks all egress traffic.

- Allowing DNS (`UDP 53`) is optional depending on cluster requirements.

- Ensure the NetworkPolicy name in the `apply` command matches the file name.

Question 6Correct

Create a service account named `backend-qa` in the `qa` namespace that cannot access any secrets.

Update the existing `frontend` Pod to use this service account.

Your answer is correct

solution

#### Explanation

By creating a service account without secret permissions and binding it to the Pod, we ensure the Pod cannot read secrets while still being able to access its own Pod resources.



**Commands / Steps**



1. # Create the service account
2. kubectl create serviceaccount backend-qa -n qa

3. # Create a Role that allows only pod access (no secret access)
4. kubectl create role no-secret-access -n qa --verb=get,list --resource=pods

5. # deny-secrets-role.yaml
6. apiVersion: rbac.authorization.k8s.io/v1
7. kind: Role
8. metadata:
9.   name: no-secret-access
10.   namespace: qa
11. rules:
12.   # Only allow access to pods
13.   - apiGroups: [""]
14.     resources: ["pods"]
15.     verbs: ["get", "list"]



16. # Bind the Role to the service account
17. kubectl create rolebinding backend-qa-nosecret --role=no-secret-access --serviceaccount=qa:backend-qa -n qa

18. # Edit the frontend Pod manifest to use the new service account
19. vim /home/pod-manifest/frontend-pod.yaml



20. # /home/cert_masters/frontend-pod.yaml
21. apiVersion: v1
22. kind: Pod
23. metadata:
24.   name: frontend
25.   namespace: qa
26. spec:
27.   serviceAccountName: backend-qa       # Use the restricted service account
28.   containers:
29.     - name: frontend
30.       image: nginx



31. # Apply the updated Pod manifest
32. kubectl apply -f /home/cert_masters/frontend-pod.yaml

33. # Verify the service account is assigned
34. kubectl get pod frontend -n qa -o jsonpath='{.spec.serviceAccountName}'

35. # Test secret access for the service account (should be denied)
36. kubectl auth can-i list secrets --as=system:serviceaccount:qa:backend-qa -n qa



**Verification Step:**

- The Pod should be running using the `backend-qa` service account.

- The command `kubectl auth can-i list secrets --as=system:serviceaccount:qa:backend-qa -n qa` must return `no`

- Ensures least privilege: `backend-qa` can only interact with Pods, no access to secrets.

- Any existing RoleBindings that grant secret access to this service account must be removed.

- This approach maintains namespace isolation while restricting sensitive operations.

Question 7Correct

Use **Falco** or **Sysdig** to monitor a single-container Pod named `tomcat` for anomalous process activity.

Detect processes that spawn or execute unusual commands over a period of at least 40 seconds.

Store detected incidents on the worker node in `/home/anomalous/report` with the format `[timestamp],[uid],[processName]`.

Your answer is correct

solution

#### Explanation

**Falco** and **Sysdig** can monitor container activity in real time.
Here, a `**custom Falco rule**` captures newly executed processes inside containers.
The incident file is stored on the worker node to comply with best practices and avoid moving sensitive data to the master.



**Commands / Steps**



**Step 1: Connect to the worker node**



1. # Connect to the worker node
2. ssh node-01
3. sudo -i

4. # Edit Falco rules to detect container drift
5. vim /etc/falco/falco_rules.local.yaml



**Step 2: Add the following rule**



1. - rule: Container Drift Detected
2.   desc: New executable created in a container
3.   condition: >
4.     evt.type in (open,openat,creat) and evt.is_open_exec=true and container
5.     and not runc_writing_exec_fifo and not runc_var_lib_docker
6.     and not user_known_container_drift_activities and evt.rawres>=0
7.   output:
8.     [%evt.time],[%user.uid],[%proc.name]
9.   priority: ERROR
10.   tags: [security]



**Step 3:  Check Falco service, PID and logs**



1. # Check Falco service and PID
2. systemctl cat falco.service
3. cat /var/run/falco.pid

4. # Reload Falco to pick up the new rules
5. kill -1 $(cat /var/run/falco.pid)

6. # Or restart the service
7. systemctl restart falco.service
8. systemctl status falco.service

9. # Check Falco logs
10. journalctl -f -u falco.service  | grep -oP '<incident format to match>'



**Step 4: If installed as a binary, run** `**falco**` **manually against the local rules**



1. # Run falco manually against the local rules
2. falco -U -r /etc/falco/falco_rules.local.yaml

3. # Capture incidents and filter them for the report
4. falco -M 500 -r /etc/falco/falco_rules.local.yaml | grep -oP '<incident format to match>'

5. # Save the filtered output to the report file
6. vim /home/anomalous/report



`**Optional**`**: Check or configure output file location**



1. grep -i log /etc/falco/falco.yaml
2. grep -i file_output -A 3 /etc/falco/falco.yaml

3. vim /etc/falco/falco.yaml
4. # Example configuration for file output
5. file_output:
6.   enabled: true
7.   keep_alive: false
8.   filename: /opt/node-01/alerts/details

9. # Exit the worker node session
10. exit



⚠️ Note:

- Ensure **Falco** is installed and running on the worker node.

- Adjust the `**falco rule**` conditions based on your specific requirements.

- The rule captures newly executed processes inside containers only.

- `**evt.rawres>=0**` ensures only successful executions are captured

- Output format `**[timestamp],[uid],[processName]**` must be preserved for the incident report

- The `**-M 500**` flag in `**falco -M 500**` sets the maximum number of events to process per second.

- This is useful for performance tuning, if your system generates a huge number of system calls, limiting the rate prevents **Falco** from being overwhelmed.

- The `**-U**` flag in `**falco -U**` ensures **Falco** runs in unbuffered mode.

- The `**-r**` flag in `**falco -r**` tells **Falco** which `**rules file**` to use. Here, `/etc/falco/falco_rules.local.yaml` is a `**custom rules file**`.

- **Falco** evaluates system activity against these rules and triggers alerts when something matches.

- Falco logs must remain on the worker node; do not transfer raw logs to master.

- **Sysdig** can also be used to observe process activity but **Falco** provides more automated detection.

Question 8Correct

Enable audit logging in the cluster. Configure log backend with the following requirements:

- Logs are stored at `/var/log/kubernetes-logs.log`.

- Logs are retained for 5 days.

- Up to 10 old log files are retained.

- A base policy exists at `/etc/audit/audit-policy.yaml` (only specifies what not to log). Extend it to:

    1. Log Node changes at `**RequestResponse**` level.

    2. Log PersistentVolumeClaim (PVC) changes in the `frontend` namespace including the `**request body**`.


Your answer is correct

solution

#### Explanation

Audit logging is configured via the `kube-apiserver`. The policy file defines which requests to log and at which level. Logs can be rotated and retained using backend flags.



**Commands / Steps**



**Step 1:  Edit the audit policy file**



1. vim /etc/audit/audit-policy.yaml



2. # /etc/audit/audit-policy.yaml
3. apiVersion: audit.k8s.io/v1
4. kind: Policy
5. rules:
6.   # 1. Log Node changes at RequestResponse level
7.   - level: RequestResponse
8.     resources:
9.     - group: ""       # core API group
10.       resources: ["nodes"]

11.   # 2. Log PVC changes in 'frontend' namespace with request body
12.   - level: Request
13.     namespaces: ["frontend"]
14.     resources:
15.     - group: ""       # core API group
16.       resources: ["persistentvolumeclaims"]

17.   # Default rule from base policy — do not log other requests
18.   - level: None



**Step 2:** **Edit** `**kube-apiserver**` **static pod manifest**



1. vim /etc/kubernetes/manifests/kube-apiserver.yaml



2. # /etc/kubernetes/manifests/kube-apiserver.yaml (relevant section)
3. spec:
4.   containers:
5.   - name: kube-apiserver
6.     image: k8s.gcr.io/kube-apiserver:v1.30.0
7.     command:
8.     - kube-apiserver
9.     - --audit-policy-file=/etc/audit/audit-policy.yaml
10.     - --audit-log-path=/var/log/kubernetes-logs.log
11.     - --audit-log-maxage=5
12.     - --audit-log-maxbackup=10
13.     - --audit-log-maxsize=100   # Max size in MB before rotation

14.     volumeMounts:
15.     - mountPath: /etc/audit/audit-policy.yaml
16.       name: audit
17.       readOnly: true
18.     - mountPath: /var/log/
19.       name: audit-log
20.       readOnly: false

21.   volumes:
22.   - name: audit
23.     hostPath:
24.       path: /etc/audit/audit-policy.yaml
25.       type: File
26.   - name: audit-log
27.     hostPath:
28.       path: /var/log/
29.       type: DirectoryOrCreate



**Verification Step:**

- Verify kube-apiserver has audit flags enabled


1. ps aux | grep kube-apiserver | grep audit

- Trigger a Node change:


1.  kubectl delete node <node-name>

- Trigger a PVC change in frontend namespace:


1. vim pvc.yaml



2. # pvc.yaml
3. apiVersion: v1
4. kind: PersistentVolumeClaim
5. metadata:
6.   name: test-pvc
7. spec:
8.   accessModes:
9.     - ReadWriteOnce
10.   resources:
11.     requests:
12.       storage: 1Gi



13. kubectl apply -f pvc.yaml --namespace frontend



- Check the logs:


1. sudo tail -f /var/log/kubernetes-logs.log | grep "nodes"
2. sudo tail -f /var/log/kubernetes-logs.log | grep "persistentvolumeclaims"



⚠️ Note:

- The `RequestResponse` level captures both metadata and request/response body.

- The PVC rule is scoped to the `frontend` namespace only.

- Audit log rotation ensures files don’t grow indefinitely and are managed automatically

Question 9Correct

A development team needs to securely provide configuration data and credentials to their applications inside Kubernetes. 

You are required to work with Kubernetes Secrets and ensure the data is mounted into a Pod for application usage.

- Retrieve the CA certificate data from the existing secret `**default-token-xxxxx**` in the `**dev**` namespace and save it to a file named `**ca.crt**`.

         - `**APP_USER=appadmin**`

         - `**APP_PASS=Sup3rS3cret**`

solution

**Verification Step:**

Secrets are base64-encoded by default in Kubernetes. Treat the `**ca.crt**` file and credential data as sensitive information.
