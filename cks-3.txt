Question 1

Enforce a prepared AppArmor profile on a Kubernetes Pod:

- Apply the `nginx-deny` AppArmor profile on a worker node.
    
- Modify the Pod manifest to use this profile.
    
- Deploy the Pod and verify that the profile restricts file write operations.
    



solution

#### Explanation

AppArmor provides mandatory access control for processes, allowing you to restrict what a container can do. In this task, the `nginx-deny` profile denies all file writes. Depending on the Kubernetes version, AppArmor can be applied via annotations (<v1.30) or `securityContext` (≥v1.30).

  

**Commands / Steps:**

  

1. # SSH into the cluster node to deploy the AppArmor profile
2. ssh cluster-node01

3. # View the prepared AppArmor profile
4. head /etc/apparmor.d/nginx_apparmor

5. # profile example
6. `#include <tunables/global>
7. profile nginx-deny flags=(attach_disconnected) {
8.     #include <abstractions/base>
9.     file,
10.     # Deny all file writes.
11.     deny /** w,
12. }`

13. # Load the AppArmor profile
14. apparmor_parser -q /etc/apparmor.d/nginx_apparmor

15. # Check if the profile is loaded
16. aa-status | grep nginx-deny

17. # Exit the node
18. exit

  

19. # Kubernetes Pod manifest for K8s ≥ 1.30
20. apiVersion: v1
21. kind: Pod
22. metadata:
23.   name: nginx-pod
24. spec:
25.   containers:
26.   - name: nginx-pod
27.     image: nginx:1.19.0
28.     ports:
29.     - containerPort: 80
30.     securityContext:
31.       appArmorProfile:
32.         type: Localhost
33.         localhostProfile: nginx-deny

  

34. # Kubernetes Pod manifest for K8s < 1.30 (using annotations)
35. apiVersion: v1
36. kind: Pod
37. metadata:
38.   name: nginx-pod
39.   annotations:
40.     container.apparmor.security.beta.kubernetes.io/nginx-pod: localhost/nginx-deny
41. spec:
42.   containers:
43.   - name: nginx-pod
44.     image: nginx:1.19.0
45.     ports:
46.     - containerPort: 80

  

47. # Apply the manifest (replace with correct filename)
48. kubectl apply -f nginx-pod.yaml

49. # Verify the Pod is running
50. kubectl get pods nginx-pod

51. # Test the restriction by attempting to write to a denied directory inside the Pod
52. kubectl exec -it nginx-pod -- /bin/sh
53. touch /restricted-directory/testfile
54. # The operation should fail due to AppArmor restrictions
55. exit

  

⚠️ Note:

- Prior to Kubernetes v1.30, AppArmor profiles were specified using annotations.
    
- Container-level AppArmor profiles take precedence over pod-level profiles.
    
- Always verify which K8s version you are using to apply the correct method.

Enable and configure Kubernetes audit logging with specific retention, size, and logging policies:

- Store audit logs at `/var/log/kubernetes-logs.log`.
    
- Retain logs for 12 days and keep a maximum of 8 old log files.
    
- Rotate logs when they reach 200MB.
    
- Extend the audit policy to log:
    
    1. Namespace changes at `RequestResponse` level.
        
    2. Request body of secret changes in the `kube-system` namespace.
        
    3. All other resources in core and extensions at `Request` level.
        
    4. `"pods/portforward"` and `"services/proxy"` at `Metadata` level.
        
    5. Omit the stage `RequestReceived`.
        
    6. Default all other requests at `Metadata` level.
        



solution

#### Explanation

Kubernetes audit logging allows tracking API requests for security and compliance. This task configures the audit backend to store logs on disk with rotation and retention settings, while specifying detailed rules for different resource types and namespaces.

  

**Commands / Steps:**

  

1. # Edit the audit policy file
2. vim /etc/audit/audit-policy.yaml

  

3. # /etc/audit/audit-policy.yaml
4. apiVersion: audit.k8s.io/v1
5. kind: Policy
6. omitStages:
7.   - "RequestReceived"
8. rules:
9.   # 1. Log namespace changes at RequestResponse level
10.   - level: RequestResponse
11.     resources:
12.       - group: ""   # core API group
13.         resources: ["namespaces"]

14.   # 2. Log request body of secret changes in kube-system
15.   - level: Request
16.     namespaces: ["kube-system"]
17.     resources:
18.       - group: ""
19.         resources: ["secrets"]

20.   # 3. Log all other core and extensions resources at Request level
21.   - level: Request
22.     resources:
23.       - group: ""           # core
24.       - group: "extensions" # deprecated API group

25.   # 4. Log pods/portforward, services/proxy at Metadata level
26.   - level: Metadata
27.     resources:
28.       - group: "" 
29.         resources: ["pods/portforward", "services/proxy"]

30.   # 5. Default: all other requests at Metadata level
31.   - level: Metadata

  

32. # Edit the kube-apiserver manifest to enable audit logging
33. vim /etc/kubernetes/manifests/kube-apiserver.yaml

  

34. # kube-apiserver.yaml snippet
35. spec:
36.   containers:
37.   - name: kube-apiserver
38.     image: k8s.gcr.io/kube-apiserver:v1.30.0
39.     command:
40.       - kube-apiserver
41.       - --audit-policy-file=/etc/audit/audit-policy.yaml
42.       - --audit-log-path=/var/log/kubernetes-logs.log
43.       - --audit-log-maxage=12
44.       - --audit-log-maxbackup=8
45.       - --audit-log-maxsize=200
46.     volumeMounts:
47.       - mountPath: /etc/audit/audit-policy.yaml
48.         name: audit
49.         readOnly: true
50.       - mountPath: /var/log/
51.         name: audit-log
52.         readOnly: false
53.   volumes:
54.     - name: audit
55.       hostPath:
56.         path: /etc/audit/audit-policy.yaml
57.         type: File
58.     - name: audit-log
59.       hostPath:
60.         path: /var/log/
61.         type: DirectoryOrCreate

  

**Verification Step:**

- Verify that audit logs are being generated:
    

1. tail -f /var/log/kubernetes-logs.log

  

⚠️ Note:

- Ensure that the kube-apiserver Pod is restarted after modifying its manifest to pick up the new audit configuration.
    
- The `extensions` API group is deprecated; it is included here for backward compatibility.
    
- Audit policy stages and levels (`RequestResponse`, `Request`, `Metadata`) define the verbosity of the logged information

Monitor container behavior on a worker node using Falco or any similar tool to detect newly spawning and executing processes:

- Analyze containers for at least 30 seconds using process execution filters.
    
- Store detected incidents in `/opt/node-01/alerts/details` in the format: `timestamp,uid/username,processName`.
    
- Example of a properly formatted incident file:
    

1. 2025-08-10T17:45:17.123Z,root,init
2. 2025-08-10T17:45:20.124Z,1001,bash
3. 2025-08-10T17:45:25.125Z,1002,sleep
4. 2025-08-10T17:45:30.125Z,1010,curl



solution

#### Explanation

Falco is a runtime security tool that monitors system calls and detects anomalous container behavior. This task configures Falco to log newly spawned processes into a structured incident file.

  

**Commands / Steps:**

  

1. # SSH into the worker node
2. ssh node-01

3. # Switch to root
4. sudo -i

5. # Inspect Falco configuration directory
6. ls -l /etc/falco

7. # Edit custom Falco rules
8. vim /etc/falco/falco_rules.local.yaml

  

9. # Example Falco rule to detect new executable creation in containers
10. - rule: Container Drift Detected
11.   desc: New executable created in a container
12.   condition: >
13.     evt.type in (open,openat,creat) and evt.is_open_exec=true and container
14.     and not runc_writing_exec_fifo
15.     and not runc_var_lib_docker and not user_known_container_drift_activities
16.     and evt.rawres>=0
17.   output:
18.     %evt.time,%user.uid,%proc.name
19.   priority: ERROR
20.   tags: [security]

  

21. # Edit Falco main configuration for logging output
22. vim /etc/falco/falco.yaml

  

23. # Example file output configuration
24. log_stderr: true
25. log_syslog: true
26. log_file: /opt/node-01/alerts/details

27. # Or on newer versions
28. file_output:
29.   enabled: true
30.   keep_alive: false
31.   filename: /opt/node-01/alerts/details

  

32. # Verify Falco configuration
33. grep -i log /etc/falco/falco.yaml
34. grep -i file_output -A 3 /etc/falco/falco.yaml

35. # Start or restart Falco service
36. systemctl status falco.service
37. systemctl start falco.service
38. # or if Falco installed as a binary
39. falco -U -r /etc/falco/falco_rules.local.yaml
40. falco -M 500 -r /etc/falco/falco_rules.local.yaml

41. # Exit the node
42. exit

  

**Verification Step:**

- Monitor the incident file for detected events:
    

1. tail -f /opt/node-01/alerts/details

- Confirm that each line follows the format: timestamp,uid/username,processName
    
- Ensure new container processes are detected within ~30 seconds of execution.
    

  

⚠️ Note:

- Falco rules can be customized to include or exclude specific containers or events.
    
- Ensure Falco has sufficient permissions to monitor container processes.
    
- File-based logging path must exist (/opt/node-01/alerts/) and be writable by Falco.

Question 8Correct

Create a PodSecurityPolicy that blocks privileged Pods within a specific namespace.

- Define a PodSecurityPolicy named `prevent-psp-policy` that disallows privileged containers.
    
- Set up a ClusterRole `restrict-access-role` that grants access to this policy.
    
- Add a ServiceAccount `psp-restrict-sa` inside the `staging` namespace.
    
- Bind the ClusterRole to the ServiceAccount using a ClusterRoleBinding `restrict-access-bind`.
    



solution

#### Explanation

Admission Controler `**PodSecurityPolicy**` must be enabled.

PodSecurityPolicy (PSP) allows administrators to enforce security restrictions at the cluster level. In this task, the PSP is configured to prevent privileged Pods from running. The associated RBAC rules ensure that only the defined ServiceAccount in the `staging` namespace can use this policy.

⚠️ Note: PSP is deprecated as of Kubernetes v1.25; for newer versions, Pod Security Admission, Kyverno, or OPA/Gatekeeper should be used.

  

**Commands / Steps:**

  

1. # Apply the PodSecurityPolicy
2. kubectl create -f prevent-psp-policy.yaml

  

3. # prevent-psp-policy.yaml
4. apiVersion: policy/v1beta1
5. kind: PodSecurityPolicy
6. metadata:
7.   name: prevent-psp-policy
8. spec:
9.   privileged: false                # ❗ privileged containers running prohibition
10.   allowPrivilegeEscalation: false
11.   requiredDropCapabilities:
12.     - ALL
13.   volumes:
14.     - configMap
15.     - emptyDir
16.     - projected
17.     - secret
18.     - downwardAPI
19.     - persistentVolumeClaim
20.   runAsUser:
21.     rule: MustRunAsNonRoot
22.   seLinux:
23.     rule: RunAsAny
24.   supplementalGroups:
25.     rule: RunAsAny
26.   fsGroup:
27.     rule: RunAsAny
28.   readOnlyRootFilesystem: true

  

29. # Create a ClusterRole that provides access to this PSP
30. kubectl create clusterrole restrict-access-role \
31.   --verb=use \
32.   --resource=podsecuritypolicies.policy \
33.   --resource-name=prevent-psp-policy \
34.   --dry-run=client -o yaml | kubectl apply -f -

  

35. # ClusterRole definition
36. apiVersion: rbac.authorization.k8s.io/v1
37. kind: ClusterRole
38. metadata:
39.   name: restrict-access-role
40. rules:
41.   - apiGroups: ["policy"]
42.     resources: ["podsecuritypolicies"]
43.     verbs: ["use"]
44.     resourceNames: ["prevent-psp-policy"]

  

45. # Create a ServiceAccount in the staging namespace
46. kubectl create serviceaccount psp-restrict-sa -n staging

  

47. # ServiceAccount definition
48. apiVersion: v1
49. kind: ServiceAccount
50. metadata:
51.   name: psp-restrict-sa
52.   namespace: staging

  

53. # Create a ClusterRoleBinding to bind the ServiceAccount to the ClusterRole
54. kubectl create clusterrolebinding restrict-access-bind \
55.   --clusterrole=restrict-access-role \
56.   --serviceaccount=staging:psp-restrict-sa \
57.   --dry-run=client -o yaml | kubectl apply -f -

  

58. # ClusterRoleBinding definition
59. apiVersion: rbac.authorization.k8s.io/v1
60. kind: ClusterRoleBinding
61. metadata:
62.   name: restrict-access-bind
63. roleRef:
64.   apiGroup: rbac.authorization.k8s.io
65.   kind: ClusterRole
66.   name: restrict-access-role
67. subjects:
68.   - kind: ServiceAccount
69.     name: psp-restrict-sa
70.     namespace: staging

Question 9Correct

Create a new Kubernetes user, approve its certificate, and assign namespace-specific permissions:

- Create a user `john` and generate a Certificate Signing Request (CSR).
    
- Approve the CSR and retrieve the signed certificate.
    
- Create a Role `john-role` in namespace `john` to allow `list`, `get`, `create`, and `delete` on `pods` and `secrets`.
    
- Create a RoleBinding `john-role-binding` to attach the Role to user `john`.
    
- Verify permissions using `kubectl auth can-i`.
    



solution

#### Explanation

Kubernetes client authentication is certificate-based. This task demonstrates creating a user with a signed certificate, configuring kubeconfig, and enforcing namespace RBAC permissions.

  

**Commands / Steps:**

  

1. # Switch to root
2. sudo -i

3. # Create namespace for the user
4. kubectl create namespace john

5. # Generate private key and CSR for user john
6. openssl genrsa -out john.key 3072
7. openssl req -new -key john.key -out john.csr -subj "/CN=john/O=devs"

8. # Encode CSR for Kubernetes
9. cat john.csr | base64 | tr -d "\n"

  

10. # Create CSR object in Kubernetes
11. cat <<EOF | kubectl apply -f -
12. apiVersion: certificates.k8s.io/v1
13. kind: CertificateSigningRequest
14. metadata:
15.   name: john-csr

**_Purpose of Audiences:_**

- Audiences are a security mechanism used to prevent token replay attacks and ensure that a token is only used by its intended recipient.
    
- By specifying audiences, you ensure that a ServiceAccount token issued for a specific purpose (e.g., accessing the Kubernetes API) cannot be misused by another service or application that is not the intended audience.
